# Public access, downloads, and license delivery

Status: implementation design, 2026-10-06. Production enrollment, checkout, artifact publication, and enforcement remain gated by the release and legal reviews.

## Separate identities

The public 127Vaults account owns orders, invoices, plan changes, download access, support requests, and Cloud tenant control ownership. It never contains a master password, account secret, vault key, device key, or decrypted item. A self-hosted installation has its own owner bootstrap and invite-only account registration under [ADR-0015](../adr/0015-account-onboarding-and-sessions.md). A public-site account is separate from every vault account. In Cloud, its verified identity may administer a tenant without consuming a vault seat or gaining vault access. If the same person also enrolls as a vault user, that separate vault account consumes a seat.

## Customer journey

The stage-by-stage self-hosted audit and supervised test sequence are in [self-hosted customer journey](../product/self-hosted-customer-journey.md).

1. The static site explains the plans and offers one clear action per plan. Until billing and release artifacts are ready, it accepts an access request with contact email, intended plan, and optional organization name through a separately deployed intake service. Do not accept vault credentials, payment card data, or license files in this form. Show explicit request status and a privacy notice. A static `npx serve` process cannot receive or store requests.
2. Razorpay is the proposed first checkout provider for an India-based merchant, subject to merchant onboarding and a live eligibility check. Its [Subscriptions offering](https://razorpay.com/subscriptions/) supports hosted links and international cards; [Stripe currently requires invitations for new India accounts](https://support.stripe.com/questions/stripe-accounts-are-invite-only-in-india?locale=en-GB). This is a product choice, not an active integration. Once checkout is reviewed, the billing service creates a public customer record and an order from a server-confirmed plan catalogue. Never trust a price, seat count, or commitment from browser fields. Idempotent signed payment events move the order to paid; a return URL alone does not. Cloud provisioning and self-hosted entitlement issuance happen only after that transition.
3. A release catalogue lists each platform artifact, version, channel, size, digest, signature, signing key ID, release-specific BSL parameters, and minimum compatible server version. The Download page renders only published catalogue entries. It must show a clear unavailable state before an approved release exists. Downloads come from immutable artifact URLs with independently verifiable signatures and checksums; no client executable is generated by the static site.
4. On a self-hosted server, the operator reads the installation ID locally and supplies it in the customer portal. The issuer signs an entitlement for that installation and plan. The portal offers the signed file for download. The operator installs it using a local authenticated workflow; clients never upload the file to the public site.
5. The server verifies issuer signature, key ID, installation binding, schema, dates, plan, major-version scope, user cap, and monotonically increasing sequence. It persists the accepted file and highest sequence for rollback protection. The server alone decides active, read-only grace, or locked state. Clients receive a redacted status API response and explain the impact; they do not independently enforce billing from a local clock.

## Entitlement v1 contract

The file is a small JSON envelope with `schemaVersion`, `keyId`, `payload` (base64url UTF-8 JSON), and `signature` (base64url Ed25519). The signature covers the exact payload bytes with a domain separator. The payload contains `licenseId`, `installationId`, `plan` (`personal` or `commercial`), `majorVersion` for Personal, `maxActiveUsers`, `issuedAt`, `notBefore`, `expiresAt`, and an increasing `sequence`. Cloud is a service entitlement in the billing control plane, not a downloadable self-hosted license file.

The issuer private key stays outside the repository and outside customer installations. The server receives only pinned public keys. Renewal and no-charge Personal user-cap increases issue a higher sequence for the same installation. A license never carries vault keys. A downgrade, invalid signature, wrong installation, unsupported schema, or expired file cannot silently replace the last accepted entitlement.

Under [ADR-0004](../adr/0004-license-state-is-not-key-destruction.md), expiry yields 30 days of read-only access, then locked access until renewal, while ciphertext, envelopes, and backups remain intact. Emergency export, clock rollback, offline client behavior, and restoration must be specified and tested before enforcement is switched on. During the current experimental phase, license status may be displayed but must not be represented as production enforcement.

## Client behavior

| Surface | License and download behavior |
| --- | --- |
| Server/operator UI | Show installation ID, plan, active-user cap and count, expiry, grace end, and safe replacement-file workflow. Only an authorized owner/operator installs a license. Do not show billing contact data to vault users. |
| Web client | Read redacted server status after authentication; show active/grace/locked messaging and avoid promising writes when server is read-only. Never put license validation in delivered JavaScript alone. |
| Desktop and CLI | Cache the last authenticated server status for explanation only. Offline unlock remains a cryptographic decision; queued edits, reconciliation, grace timing, and emergency export need a server-backed policy before enforcement. The CLI should expose `license status` without exposing the signed file or issuer material. |
| Browser extension | Display a short source status when the connected client/server is in grace or locked state. Keep its read-only fill path tied to the chosen source's established unlock and policy; no separate public-site login. |

## Delivery gates

The first end-to-end test uses only fictitious users, an ephemeral test issuer key, a disposable installation, and unpublished artifacts. Production requires reviewed legal terms, an approved checkout provider, payment/webhook reconciliation, anti-abuse controls, a privacy/retention policy for contact data, a signed release, safe license replacement and rollback tests, and the existing beta-readiness gate. Do not advertise a download or accept payment until its corresponding artifact and entitlement path have passed those gates.

The current code provides a plan-aware static waitlist page, a separate experimental intake API with encrypted local records, a validated but empty release catalogue, a signed-license verifier, a test issuer, local installation, and an authenticated server status endpoint. A configured signed license limits active users plus live invitation reservations during invitation creation and redemption. It also blocks vault and invitation writes in read-only or locked mode while leaving sign-in, reads, device recovery, and vault restoration available. The status endpoint reports `enforcement: vault-writes-and-seats` for a signed license and `disabled` for an unlicensed experimental installation. Full license enforcement remains incomplete: anti-rollback state is local to the installer, clock rollback and emergency export need a settled policy, and some account/device mutations remain available. Payment processing, production release signing, and public client files are not available.
