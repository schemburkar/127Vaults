SECURITY / TECHNICAL DETAILS

The encryption design, in detail.

A technical overview of vault encryption, key derivation and synchronization. Parameters describe the current implementation.

PASSWORD-BASED DERIVATION

Argon2id: memory and computation.

The vault root-key envelope uses Argon2id version 1.3 with 64 MiB (65,536 KiB) of memory, 3 passes, 1 lane and a 32-byte output. Each root-key creation or password rewrap generates a fresh 16-byte salt.

The password-derived result and the account Secret Key feed the HKDF-SHA-256 key derivation used to protect the random root key. Vault keys and record keys have separate derivation contexts.

Argon2 pass counts are not comparable to the large iteration counts quoted for PBKDF2. Memory cost, passes and parallelism are separate parameters; a larger-looking iteration number alone does not establish stronger protection. These parameters do not make a weak or exposed credential safe.

Primitive reference: Argon2 (RFC 9106).

VAULT RECORD PROTECTION

Encrypt and authenticate.

01 / ENCRYPTION

XChaCha20-Poly1305

The current vault envelope uses a 256-bit key, a fresh 192-bit nonce and a 128-bit authentication tag. Authenticated context binds records to their purpose and identifiers.

02 / DERIVATION

HKDF-SHA-256

Separate labeled contexts derive keys for different roles. Password-derived material protects a random root key; vault encryption uses a key hierarchy rather than encrypting every record directly with the password.

03 / AUTHENTICATION

OPAQUE

Account authentication uses an OPAQUE profile with Ristretto255, TripleDH and SHA-512. Its client stretching also uses Argon2id with 64 MiB, 3 passes and 1 lane. Authentication and vault decryption are separate roles.

STORAGE AND SYNCHRONIZATION

Persistent ciphertext. Local decryption.

Your self-hosted server persists encrypted vault records and sync history so authorized devices can synchronize asynchronously. Server backups can also retain encrypted records. Treat server storage and backups as durable data, not a disposable relay queue.

Clients encrypt item indexes and item bodies. Account, device and synchronization metadata still exist on the server; this design does not claim complete metadata anonymity. Authorized desktop and CLI clients retain encrypted local replicas for offline use.

Device enrollment is an explicit trust transition. Revocation limits future access but cannot recall plaintext or keys already obtained by a previously authorized device.

CLIENT TRUST

The boundaries matter.

Encryption at rest protects stored vault ciphertext. A compromised, unlocked operating system can still observe secrets as they are used. Clipboard copies, plaintext exports and recovery material require separate care.

The web vault loads code from your server. An active server compromise could replace that code and capture credentials or plaintext at unlock. Installed clients reduce reliance on server-delivered web code, but still require a trusted installation and update path.

Further reading: HKDF (RFC 5869).
