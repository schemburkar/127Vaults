# Internal regional Cloud database tools

These tools are source-tree operator experiments. The self-hosted server image copies `apps/server/src`, not this directory. Its executable refuses `VAULTS_ACCESS_MODE=regional-cloud`, and its schema check rejects a database with a `cloud` schema. Do not run these tools against a self-hosted database, admit customer data, or advertise Cloud availability.

`cli.mjs` requires `VAULTS_INTERNAL_CLOUD_OPERATIONS=1`, an explicit non-default `VAULTS_DATABASE_NAME`, `VAULTS_DATABASE_HOST`, and the existing restricted `VAULTS_DATABASE_PASSWORD_FILE`. It fixes the internal location to `global`. Run `initialize`, `verify`, or `reserve <canonical-host>`. `prepare <canonical-host>` requires `VAULTS_OPAQUE_NODE_MODULE` and stores tenant OPAQUE setup. `bootstrap <canonical-host>` requires `VAULTS_TOKEN_KEY_FILE` and a new `VAULTS_CLOUD_BOOTSTRAP_OUTPUT` path; the token is written only to that restricted file, never stdout. `initialize` accepts only an empty database. There is intentionally no CLI activation command. The operator role must be able to create a database role and schemas. Do not use the self-hosted runtime database credential for production Cloud operations.

The overlay creates a no-login `vaults_cloud_runtime` role, RLS policies on every tenant table, an operator-only tenant catalog, and a policy inventory check. A future Cloud runtime must use a separate login role without schema ownership, superuser rights, or `BYPASSRLS`, and must set tenant context only from verified request identity inside each transaction. The internal request boundary implements those checks, but no listener mounts it.

The first deployment uses one internal location key, `global`. It is not a customer region choice or a promise of worldwide data residency. The catalog separately records a control owner identity ID and email. That public/customer identity grants no vault access and consumes no vault seat; verification and authorization of that identity still need the public control plane. The local lifecycle functions reserve a tenant, link its verified control owner, prepare OPAQUE setup, then activate only after a vault owner account, credentials, active device, and consumed bootstrap token exist. The CLI can prepare and issue a bootstrap capability, but cannot activate a tenant. An internal prepared-tenant request boundary admits only the ceremony and first vault-owner registration routes; a separate active-tenant boundary handles ordinary API traffic. No listener imports either boundary.

`request-boundary.mjs`, `scoped-pool.mjs`, and `tenant-handlers.mjs` compose the two internal request paths. They verify direct TLS/SNI/Host/Origin, use restricted database tenant resolvers, check the login role, and give every mounted store a transaction-scoped tenant pool. The active path mounts authentication, device, sync, vault, and settings handlers. Tenant-scoped invitations mount when a mailer is explicitly supplied; billing, licensing, and operator administration remain unavailable. No listener imports this composition, so Cloud remains unavailable.

The active boundary serves `GET /api/v1/cloud/discovery` as a versioned, no-store response with the routed tenant UUID, canonical HTTPS origin, internal location key, API/sync protocol versions, OPAQUE server public key, and checkpoint public key. It returns no account or vault information. Direct TLS with matching SNI and canonical Host authenticates the origin; clients must pin the returned tenant and keys during trusted enrollment and reject later changes until a reviewed rotation or move flow exists. Prepared, suspended, and unknown tenants cannot reach discovery. Aliases and redirects are not supported.

Run the disposable PostgreSQL rehearsal with `VAULTS_INTERNAL_CLOUD_LIVE_TEST=1 node scripts/internal-cloud-rehearsal.mjs` on a host with Podman and the PostgreSQL 17 image. It creates a randomly named ephemeral container with no persistent volume, verifies four-tenant reads/writes, connection context reset, tenant-bound login material, first-owner registration, a second user's invitation enrollment, and cross-host rejection through real HTTP handlers, then removes it. OPAQUE cryptography in this rehearsal uses a stub bridge; separate protocol tests cover the adapter. This rehearsal does not establish complete HTTP coverage, backup/restore, or production readiness.
