# Internal regional Cloud database tools

These tools are source-tree operator experiments. The self-hosted server image copies `apps/server/src`, not this directory. Its executable refuses `VAULTS_ACCESS_MODE=regional-cloud`, and its schema check rejects a database with a `cloud` schema. Do not run these tools against a self-hosted database, admit customer data, or advertise Cloud availability.

`cli.mjs` requires `VAULTS_INTERNAL_CLOUD_OPERATIONS=1`, an explicit non-default `VAULTS_DATABASE_NAME`, `VAULTS_DATABASE_HOST`, and the existing restricted `VAULTS_DATABASE_PASSWORD_FILE`. It fixes the internal location to `global`. Run `initialize`, `verify`, or `reserve <slug> <seat-limit>`. `prepare <slug>` requires `VAULTS_OPAQUE_NODE_MODULE` and stores tenant OPAQUE setup. `bootstrap <slug>` requires `VAULTS_TOKEN_KEY_FILE` and a new `VAULTS_CLOUD_BOOTSTRAP_OUTPUT` path. It writes the token only to that restricted file. `initialize` accepts only an empty database. The operator role must be able to create a database role and schemas. The pilot backlog tracks the browser-based operator workflow and deployment. [Cloud family pilot backlog](../../../docs/architecture/cloud-family-pilot-backlog.md)

For internal operations, `provision <slug> <seat-limit> <owner-id> <owner-email>` prepares the tenant atomically using the configured OPAQUE module. Supply an already verified control owner. `setup-link <slug>` writes a one-time link to the same restricted output path used by `bootstrap`. Running it again with a fresh output path replaces the prior capability until the owner enrolls. `list` and `inspect <slug>` show seat use and activation readiness. `activate`, `suspend`, and `resume` accept the tenant slug. Suspension blocks newly routed requests. Requests already routed may complete, and existing sessions retain their normal expiry when service resumes. `set-seats <slug> <seat-limit>` rejects reductions below the seats already in use or reserved.

The overlay creates a no-login `vaults_cloud_runtime` role, RLS policies on every tenant table, an operator-only tenant catalog, and a policy inventory check. The runtime requires a separate login role without schema ownership, superuser rights, or `BYPASSRLS`. The request boundary sets tenant context from the UUID resolved from the validated path slug inside each transaction. Enrollment checks the fixed seat limit within the same transaction as its existing seat count.

The first deployment uses one internal location key, `global`. The catalog separately records a control owner identity ID and email. That public/customer identity grants no vault access and consumes no vault seat. The operator links an approved control owner. Manage verifies the linked email before listing its tenant status and seats. The lifecycle functions reserve a tenant, link its verified control owner, prepare OPAQUE setup, then activate only after a vault owner account, credentials, active device, and consumed bootstrap token exist. The CLI can prepare and issue a bootstrap capability. The runtime serves the web shell, setup status, and enrollment endpoints under prepared tenant paths. Active tenants also receive the ordinary API routes.

`serve.mjs` starts the internal HTTPS listener and loads the Node OPAQUE module and signing keys. Build its local image with `pnpm cloud:build`. Configure the runtime login and private database with `VAULTS_DATABASE_USER`, `VAULTS_DATABASE_NAME`, `VAULTS_DATABASE_HOST`, and `VAULTS_DATABASE_PASSWORD_FILE`. Enable the internal runtime with `VAULTS_INTERNAL_CLOUD_OPERATIONS=1` and provide `VAULTS_TLS_CERT`, `VAULTS_TLS_KEY`, `VAULTS_TOKEN_KEY_FILE`, and `VAULTS_CHECKPOINT_KEY_FILE`. The image sets the OPAQUE module path and listens on port 8443 by default. The source entry point defaults to loopback. For direct public HTTPS, publish only the vault listener and install a publicly trusted certificate for cloud.127vaults.com. Keep PostgreSQL and management separately protected.

Run `node apps/server/internal-cloud/cli.mjs deploy` as the one-time initialization job, using the operator's database configuration. Set `VAULTS_CLOUD_RUNTIME_DATABASE_USER` to a dedicated `vaults_cloud_login_` name and `VAULTS_CLOUD_RUNTIME_DATABASE_PASSWORD_FILE` to its restricted credential file. The job initializes an empty database or verifies a matching Cloud schema, creates the runtime login when absent, and verifies it over a separate connection. A rerun leaves an existing login unchanged. Start the HTTPS process with the runtime credential after the job succeeds.

For managed PostgreSQL, set `VAULTS_CLOUD_DATABASE_CA_FILE` to the provider's CA bundle for the CLI, management listener, runtime, and backup job. The backup uses hostname verification by default. `PGSSLMODE=disable` is available for a disposable local database.

The active path mounts authentication, device, sync, vault, and settings handlers. Cloud vault owners manage the family roster, invitations and seats under Settings → Family members. Suspension revokes online sessions. An installed browser can use an already cached entitlement until its authenticated session expiry. Reactivation requires a free seat and a fresh sign-in.

The runtime serves the invitation-only landing page at `https://cloud.127vaults.com/` and a readiness check at `/healthz`. The same certificate and hostname serve every tenant at `/t/<slug>/`. Setup and member invitations link to that path. Only one tenant can be active in a browser profile. Each tenant keeps its own device identity, encrypted replica and queued operations.

Invitation delivery defaults to `VAULTS_CLOUD_INVITATION_MAIL=disabled`. Use `smtp` with the existing `SMTP_HOST`, `SMTP_PORT`, `SMTP_USERNAME`, `SMTP_PASSWORD_FILE`, and `SMTP_FROM` configuration for approved private delivery. Use `capture` for local rehearsals with direct loopback access and `VAULTS_CLOUD_MAIL_CAPTURE_DIR` pointing to an operator-owned private absolute directory. On Windows, restrict its ACL to the operator account. Capture writes a separate private JSON file per code and requires no mail provider. Delete the capture files after the rehearsal.

For Desktop, create the vault account in the browser first. Copy the family address from **Settings → Devices** and paste it into Desktop's Cloud setup. Desktop verifies public HTTPS and pins the tenant UUID, OPAQUE key, and checkpoint key. Enter your existing username and start registration. Desktop opens the family's browser approval link and waits for approval. Sign in on an already registered browser, confirm the code, and return to Desktop for the first online unlock. **Open browser approval** lets you reopen the page if the automatic launch fails. Self-hosted connections continue to use the operator-supplied CA.

For Cloudflare Tunnel on a dedicated host, run `cloudflared` beside the runtime. Set `VAULTS_CLOUD_INGRESS=cloudflare-tunnel` and `VAULTS_CLOUD_BIND=127.0.0.1`. Route directly from the tunnel to the loopback HTTPS listener with `matchSNItoHost` enabled and origin certificate verification enabled. Preserve the incoming Host and keep the origin port private. This trusts local processes on that host, so do not run untrusted workloads alongside the connector. The listener accepts one valid `CF-Connecting-IP` from loopback and ignores forwarded authority headers. Keep Workers off the tenant routes so a Worker subrequest cannot supply client metadata. [Cloudflare origin parameters](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/configure-tunnels/origin-parameters/) · [Cloudflare request headers](https://developers.cloudflare.com/fundamentals/reference/http-headers/)

For the remote pilot, the vault hostname can be public with signups closed and provisioning restricted to platform operators. A browser Access challenge on the vault hostname would require additional Desktop authentication support. Keep the management hostname on its own service-token policy and configure the Admin Worker separately. A free Worker can serve the Admin interface and forward control requests. The vault container and PostgreSQL need a host for the existing Node HTTPS runtime and database. Cloudflare Containers require Workers Paid. A provider that terminates public TLS before Node needs a trusted ingress that preserves the request authority and establishes a verified TLS connection to the app. [Workers limits](https://developers.cloudflare.com/workers/platform/limits/) · [Container pricing](https://developers.cloudflare.com/containers/platform/pricing/)

### Restart, rollback and backup

Before updating, record the image digest and keep the previous digest available. Use the deployment operator to run `cli.mjs verify`. Restart the management listener and family runtime with their own database logins and the existing key files. Check `/healthz` on the landing hostname for database readiness, then check the protected management tenant list. Roll back by restarting the previous image with the same environment and keys. If its schema check fails, stop and restore a matching snapshot into an isolated database. Do not point an older image at a schema it rejects.

From the Linux deployment host, use `node scripts/ops/cloud-backup.mjs /absolute/new-backup.vbak` with the Cloud database operator settings and mounted `VAULTS_TOKEN_KEY_FILE` and `VAULTS_CHECKPOINT_KEY_FILE`. It requires `pg_dump`, `tar`, an operator-owned mode `0700` directory in `VAULTS_CLOUD_BACKUP_SCRATCH`, and a separate encryption key in `VAULTS_CLOUD_BACKUP_KEY_FILE`. The command verifies the Cloud schema, captures the PostgreSQL dump and both runtime keys, seals them with the existing authenticated backup envelope, and verifies the ciphertext. Keep the encryption key separately. Recreate database logins and recover certificate, ingress and service credentials from the deployment secret store.

For recovery, use `node server.mjs envelope open --input <backup> --output <new-private-tar> --key-file <backup-key>`, confirm the authenticated manifest says `cloud-global` and `cloud-pilot-1`, then extract into a new private directory. In an isolated PostgreSQL cluster, create the Cloud role names used by the dump and the original schema operator role before running `pg_restore --exit-on-error --single-transaction --dbname <empty-cloud-database> <database.dump>`. Preserve the dump's permissions. Run `cli.mjs verify`, provision new restricted logins, and start the matching Cloud image with the recovered token and checkpoint keys before redirecting ingress. Hosted backup scheduling and recovery verification remain separate.

The Linux user units in `deploy/cloud-backup.service` and `deploy/cloud-backup.timer` are staged for step 35. Install them with mode `0644` in the backup operator's `~/.config/systemd/user/`. They expect the checkout at `~/127Vaults` and the backup settings at `~/.config/127vaults-cloud/backup.env`. Supply the database, runtime key, scratch, and encryption settings above plus an operator-owned mode `0700` directory in `VAULTS_CLOUD_BACKUP_OUTPUT_DIR`. Restrict the environment file to the backup operator. Adjust the checkout path and Node executable with a systemd override if needed. `node scripts/ops/cloud-backup.mjs --scheduled` writes a timestamped, authenticated backup. After provisioning, run the service once, verify the output and restore, then enable the timer for the dedicated backup operator.

### Private management API

Manage can read the Cloud directory through a separate HTTPS route. Configure `cloudCustomerDirectory.origin` and `pilotManualLogin` in the split-site deployment settings and store the dedicated `cloud-customer-directory-token` in the deployment secret directory. Mount the matching token through `VAULTS_CLOUD_CUSTOMER_DIRECTORY_TOKEN_FILE` in the management runtime. Limit this ingress to `POST /internal/cloud/v1/customer-tenants`; the operator commands use their own authenticated route. Manage looks up tenant status and the seat allowance for the signed-in control owner's verified email. An operator can use the existing manual customer code inbox to hand the code privately to an approved Cloud-only control owner when pilot manual sign-in is enabled. Send the code to the linked contact through the agreed private channel.

After `deploy`, run `node apps/server/internal-cloud/cli.mjs deploy-management` with the deployment operator's database configuration, `VAULTS_CLOUD_MANAGEMENT_DATABASE_USER` set to a dedicated `vaults_cloud_manager_` login, and `VAULTS_CLOUD_MANAGEMENT_DATABASE_PASSWORD_FILE` set to its credential file. The job verifies the existing schema and authenticates separately with the management login. Initialize a fresh database for the first hosted pilot. This overlay rejects the earlier hostname-based prototype database by checksum. Preserve any old data separately.

Run `node apps/server/internal-cloud/management.mjs` in a separate process with that login in `VAULTS_DATABASE_USER` and `VAULTS_DATABASE_PASSWORD_FILE`. Supply the TLS certificate and key, the same bootstrap token key and OPAQUE module as the vault runtime, and a separate 64-character lowercase hexadecimal secret in `VAULTS_CLOUD_MANAGEMENT_TOKEN_FILE`. The default listener is `127.0.0.1:8444`.

Send JSON POST requests to `/internal/cloud/v1/<command>` over HTTPS with the bearer service token and `X-127V-Operator`. The authenticated caller supplies the operator identifier. Keep the endpoint private and send that header only from the backend after verifying the named operator. `list` takes `{}`. `provision` takes `host`, `maxActiveUsers`, `ownerIdentityId`, and `ownerEmail`. `issue-setup`, `activate`, `suspend`, and `resume` take `host`. `set-seats` takes `host` and `maxActiveUsers`. A setup link is a credential and is returned only in the response to issuance. Successful changes record actor, action, tenant and time in the same database transaction.

The active boundary serves `GET /api/v1/cloud/discovery` as a versioned, no-store response with the routed tenant UUID, canonical HTTPS origin, internal location key, API/sync protocol versions, OPAQUE server public key, and checkpoint public key. It returns no account or vault information. Direct TLS with matching SNI and canonical Host authenticates the origin; clients must pin the returned tenant and keys during trusted enrollment and reject later changes until a reviewed rotation or move flow exists. Prepared, suspended, and unknown tenants cannot reach discovery. Aliases and redirects are not supported.

Run the disposable PostgreSQL rehearsal with `VAULTS_INTERNAL_CLOUD_LIVE_TEST=1 node tests/internal/server/cloud-rehearsal.mjs` on a host with Podman and the PostgreSQL 17 image. It creates a randomly named ephemeral container with no persistent volume, verifies four-tenant reads/writes, connection context reset, tenant-bound login material, first-owner registration, a second user's invitation enrollment, and cross-path rejection through real HTTP handlers, then removes it. OPAQUE cryptography in this rehearsal uses a stub bridge; separate protocol tests cover the adapter. This rehearsal does not establish complete HTTP coverage, backup/restore, or production readiness.

For the full local browser rehearsal, build the WASM fixture and web vault with `pnpm fixture:build` and `pnpm --filter @127vaults/web build`. Set `VAULTS_INTERNAL_CLOUD_LIVE_TEST=1` and point `VAULTS_PLAYWRIGHT_MODULE` and `VAULTS_BROWSER_EXECUTABLE` to locally installed Playwright and Chromium-based browser paths. Run `pnpm cloud:rehearse`. The real Admin page and Worker handler provision and activate two synthetic families through the management HTTPS listener. The fixture supplies a locally signed Access assertion and fake service credentials. Both families enroll with real OPAQUE, redeem captured verification mail, and recover separate synced items after signing in again. All listeners and data stay on the local fixture.
