# Internal regional Cloud database tools

These tools are source-tree operator experiments. The self-hosted server image copies `apps/server/src`, not this directory. Its executable refuses `VAULTS_ACCESS_MODE=regional-cloud`, and its schema check rejects a database with a `cloud` schema. Do not run these tools against a self-hosted database, admit customer data, or advertise Cloud availability.

`cli.mjs` requires `VAULTS_INTERNAL_CLOUD_OPERATIONS=1`, an explicit non-default `VAULTS_DATABASE_NAME`, `VAULTS_DATABASE_HOST`, and the existing restricted `VAULTS_DATABASE_PASSWORD_FILE`. It fixes the internal location to `global`. Run `initialize`, `verify`, or `reserve <canonical-host> <seat-limit>`. `prepare <canonical-host>` requires `VAULTS_OPAQUE_NODE_MODULE` and stores tenant OPAQUE setup. `bootstrap <canonical-host>` requires `VAULTS_TOKEN_KEY_FILE` and a new `VAULTS_CLOUD_BOOTSTRAP_OUTPUT` path. It writes the token only to that restricted file. `initialize` accepts only an empty database. The operator role must be able to create a database role and schemas. The pilot backlog tracks the browser-based operator workflow and deployment. [Cloud family pilot backlog](../../../docs/architecture/cloud-family-pilot-backlog.md)

For internal operations, `provision <host> <seat-limit> <owner-id> <owner-email>` prepares the tenant atomically using the configured OPAQUE module. Supply an already verified control owner. `setup-link <host>` writes a one-time link to the same restricted output path used by `bootstrap`. Running it again with a fresh output path replaces the prior capability until the owner enrolls. `list` and `inspect <host>` show seat use and activation readiness. `activate`, `suspend`, and `resume` accept the canonical host. Suspension blocks newly routed requests. Requests already routed may complete, and existing sessions retain their normal expiry when service resumes. `set-seats <host> <seat-limit>` rejects reductions below the seats already in use or reserved.

The overlay creates a no-login `vaults_cloud_runtime` role, RLS policies on every tenant table, an operator-only tenant catalog, and a policy inventory check. The runtime requires a separate login role without schema ownership, superuser rights, or `BYPASSRLS`. The request boundary sets tenant context from the verified hostname inside each transaction. Enrollment checks the fixed seat limit within the same transaction as its existing seat count.

The first deployment uses one internal location key, `global`. The catalog separately records a control owner identity ID and email. That public/customer identity grants no vault access and consumes no vault seat. Verification and authorization of that identity still need the control plane. The lifecycle functions reserve a tenant, link its verified control owner, prepare OPAQUE setup, then activate only after a vault owner account, credentials, active device, and consumed bootstrap token exist. The CLI can prepare and issue a bootstrap capability. The runtime serves the web shell, setup status, and enrollment endpoints on prepared tenant hosts. Active tenants also receive the ordinary API routes.

`serve.mjs` starts the internal HTTPS listener and loads the Node OPAQUE module and signing keys. Build its local image with `pnpm cloud:build`. Configure the runtime login and private database with `VAULTS_DATABASE_USER`, `VAULTS_DATABASE_NAME`, `VAULTS_DATABASE_HOST`, and `VAULTS_DATABASE_PASSWORD_FILE`. Enable the internal runtime with `VAULTS_INTERNAL_CLOUD_OPERATIONS=1` and provide `VAULTS_TLS_CERT`, `VAULTS_TLS_KEY`, `VAULTS_TOKEN_KEY_FILE`, and `VAULTS_CHECKPOINT_KEY_FILE`. The image sets the OPAQUE module path and listens on port 8443 by default. Keep the origin private. The source entry point defaults to loopback.

Run `node apps/server/internal-cloud/cli.mjs deploy` as the one-time initialization job, using the operator's database configuration. Set `VAULTS_CLOUD_RUNTIME_DATABASE_USER` to a dedicated `vaults_cloud_login_` name and `VAULTS_CLOUD_RUNTIME_DATABASE_PASSWORD_FILE` to its restricted credential file. The job initializes an empty database or verifies a matching Cloud schema, creates the runtime login when absent, and verifies it over a separate connection. A rerun leaves an existing login unchanged. Start the HTTPS process with the runtime credential after the job succeeds.

The active path mounts authentication, device, sync, vault, and settings handlers. Tenant-scoped invitations mount when a mailer is explicitly supplied to the server factory. Ingress integration, the admin portal connection, and pilot invitation delivery are tracked separately.

The runtime reserves `cloud.127vaults.com` for the static family entry page. Configure that hostname in the Cloud ingress certificate and routing when the pilot is deployed. Families follow their own setup or invitation link to their tenant origin. The landing hostname serves guidance and its stylesheet only.

### Private management API

After `deploy`, run `node apps/server/internal-cloud/cli.mjs deploy-management` with the deployment operator's database configuration, `VAULTS_CLOUD_MANAGEMENT_DATABASE_USER` set to a dedicated `vaults_cloud_manager_` login, and `VAULTS_CLOUD_MANAGEMENT_DATABASE_PASSWORD_FILE` set to its credential file. The job verifies the existing schema and authenticates separately with the management login. Use a newly initialized internal database for this overlay revision.

Run `node apps/server/internal-cloud/management.mjs` in a separate process with that login in `VAULTS_DATABASE_USER` and `VAULTS_DATABASE_PASSWORD_FILE`. Supply the TLS certificate and key, the same bootstrap token key and OPAQUE module as the vault runtime, `VAULTS_CLOUD_TENANT_SUFFIX` for the allowed family hostname namespace, and a separate 64-character lowercase hexadecimal secret in `VAULTS_CLOUD_MANAGEMENT_TOKEN_FILE`. The default listener is `127.0.0.1:8444`.

Send JSON POST requests to `/internal/cloud/v1/<command>` over HTTPS with the bearer service token and `X-127V-Operator`. The authenticated caller supplies the operator identifier. Keep the endpoint private and send that header only from the backend after verifying the named operator. `list` takes `{}`. `provision` takes `host`, `maxActiveUsers`, `ownerIdentityId`, and `ownerEmail`. `issue-setup`, `activate`, `suspend`, and `resume` take `host`. `set-seats` takes `host` and `maxActiveUsers`. A setup link is a credential and is returned only in the response to issuance. Successful changes record actor, action, tenant and time in the same database transaction.

The active boundary serves `GET /api/v1/cloud/discovery` as a versioned, no-store response with the routed tenant UUID, canonical HTTPS origin, internal location key, API/sync protocol versions, OPAQUE server public key, and checkpoint public key. It returns no account or vault information. Direct TLS with matching SNI and canonical Host authenticates the origin; clients must pin the returned tenant and keys during trusted enrollment and reject later changes until a reviewed rotation or move flow exists. Prepared, suspended, and unknown tenants cannot reach discovery. Aliases and redirects are not supported.

Run the disposable PostgreSQL rehearsal with `VAULTS_INTERNAL_CLOUD_LIVE_TEST=1 node tests/internal/server/cloud-rehearsal.mjs` on a host with Podman and the PostgreSQL 17 image. It creates a randomly named ephemeral container with no persistent volume, verifies four-tenant reads/writes, connection context reset, tenant-bound login material, first-owner registration, a second user's invitation enrollment, and cross-host rejection through real HTTP handlers, then removes it. OPAQUE cryptography in this rehearsal uses a stub bridge; separate protocol tests cover the adapter. This rehearsal does not establish complete HTTP coverage, backup/restore, or production readiness.
